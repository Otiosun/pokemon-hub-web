# Pokémon Control Center — Deployment Boundary

Status: deployment architecture and dedicated-project contract defined; dedicated Vercel project/hostname is still pending.

## Non-negotiable boundary

The Control Center is an administrative application, not a route of the public Pokémon Hub.

It may temporarily share this Git repository for code review and selected design assets, but production/staging deployment must have its own project, hostname, environment configuration and access policy.

## Intended topology

Public player experience:

`pokemon-hub-web -> public/player deployment`

Administrative control plane:

`control-center/ -> dedicated admin deployment -> Cloudflare Access -> Admin API`

The final administrative hostname must be protected before the application becomes operational. A public Hub deployment must never become an accidental bypass to the Control Center.

## Build boundary

Control Center root: `control-center/`

Required independent proof:

```bash
npm run verify:control-center
```

The root wrapper invokes the pinned pnpm 11.23.0 and runs `pnpm --dir control-center verify`, so Biome, TypeScript, Vitest and Vite resolve from the Control Center's own frozen dependency graph instead of the public Hub's `node_modules`.

## Dedicated Vercel project contract

`control-center/vercel.json` is the deployment contract for a Vercel project whose **Root Directory is exactly `control-center`**.

It defines:

- framework: Vite;
- install command that materializes and verifies the canonical lock source from inside `control-center/`;
- exact pnpm 11.23.0 install with `--frozen-lockfile --ignore-scripts`;
- build command that runs the Control Center's own `pnpm verify`;
- output directory `dist`.

This matters because a project rooted at `control-center/` does not execute the public Hub root `postinstall`. The admin app therefore carries everything required to reproduce and verify its own dependency graph without relying on the public deployment wrapper.

## Reproducible dependency graph

The Control Center dependency graph is intentionally fail-closed:

- package manager is pinned to `pnpm@11.23.0`;
- the committed canonical lock source is `control-center/pnpm-lock.yaml.gz.b64`;
- `control-center/scripts/materialize-lockfile.mjs` reconstructs the ordinary pnpm YAML lockfile byte-for-byte;
- the materializer requires SHA-256 `dcacde6be17cf53c6c8acaa08f1715c0e25afc1f5fdc4c27300edd4862241e72` before writing the derived YAML;
- installation then runs with `--frozen-lockfile --ignore-scripts`;
- `--no-frozen-lockfile` and `--lockfile-only` generation are prohibited in the normal build path;
- the derived `pnpm-lock.yaml` is ignored because `pnpm-lock.yaml.gz.b64` is the reviewed/versioned source of truth.

The encoded source is not an alternate dependency resolver. It is a deterministic transport representation of the exact pnpm v9 lockfile previously generated by Node 24.19.0 + pnpm 11.23.0 and verified by hash.

Dependency updates must be explicit: change `control-center/package.json`, regenerate the lock with the pinned pnpm version in a controlled proof, replace the committed encoded source, update the expected hash only after review, and require the frozen install + full Control Center verify to pass. A build must never silently refresh the graph.

## Environment contract

The app uses these browser-visible, non-secret build settings:

- `VITE_CONTROL_CENTER_ENV` — `development | staging | production`
- `VITE_CONTROL_CENTER_API_BASE_URL` — required outside development
- `VITE_CONTROL_CENTER_BUILD_LABEL` — diagnostic build/revision label

Secrets, Access service credentials, private keys, PostgreSQL credentials and WhatsApp credentials must never use `VITE_*` or enter the browser bundle.

## Required Vercel project settings

When the dedicated project is materialized, use:

- Git repository: `Otiosun/pokemon-hub-web`;
- Root Directory: `control-center`;
- Framework: Vite / use repository `vercel.json`;
- Node: 24.x, constrained by `package.json` to `>=24.19.0 <25`;
- Preview/staging API URL: the real Admin API staging endpoint only;
- `VITE_CONTROL_CENTER_ENV=staging` for the first dedicated project proof;
- a build label derived from the deployment/commit;
- no production credentials during the F1.2 proof.

A generated `*.vercel.app` hostname is sufficient to prove project/deployment separation for F1.2 if the deployment is materially independent from `pokemon-hub-web`. A friendly custom domain is not required for that engineering gate. However, the hostname must not become operational for administrators until Cloudflare Access/origin protection is configured according to the later security gates.

## Required deployment separation

A dedicated admin deployment must provide:

- independent project/deployment ID;
- dedicated admin hostname;
- environment-specific API base URL;
- explicit STAGING/PRODUCTION distinction;
- Cloudflare Access policy before operational use;
- separate Access application audience for staging and production;
- no public fallback route that bypasses Access;
- rollback history independent from the public Hub;
- deploy/smoke evidence recorded in the Control Center checkpoint.
